# Geometry laws

These are property-based tests for DeviceLayout's 2D polygon operations: the boolean
operations (`union2d`, `intersect2d`, `difference2d`, `xor2d`, `clip`, `clip_tiled`),
`offset`, the keyhole cuts that `to_polygons` makes in polygons with holes, path `halo`s,
and the coordinate handling around them (rigid transforms, units, and the conversion to
Clipper's integer grid).

Instead of checking fixed inputs against expected outputs, each test states a *law*
that should hold for every input, such as "union is commutative" or "a point is in
`A ∪ B` exactly when it is in `A` or in `B`", and checks it on inputs generated by
[Supposition.jl](https://github.com/Seelengrab/Supposition.jl). Outputs are compared as
regions of the plane, using exact rational arithmetic that never calls the clipping
library under test.

This file is the overview: how to run the laws, what a passing run does and doesn't
tell you, every law and known failure, and what isn't covered. The two tools in the
subdirectories, [mutants](mutants/README.md) and [differential](differential/README.md),
have their own short READMEs.

## Running

The laws are test items tagged `:geomlaws` in the regular test suite, so `Pkg.test()`
runs them. To run only the laws:

```julia
using TestEnv
TestEnv.activate()
using TestItemRunner
import DeviceLayout
TestItemRunner.run_tests(pkgdir(DeviceLayout); filter=ti -> :geomlaws in ti.tags)
```

or one law, by name, with `julia --project=. scripts/test.jl "GeomLaws O3"`. The whole
tag takes about two minutes at the default budget.

| Variable              | Default    | Effect                                                              |
|:--------------------- |:---------- |:------------------------------------------------------------------- |
| `GEOMLAWS_EXAMPLES`   | `50`       | Valid generated inputs per check                                    |
| `GEOMLAWS_SEED`       | `20260908` | Generator seed (`explore.jl` also takes `random`)                   |
| `GEOMLAWS_RUN_BROKEN` | `0`        | `1` runs the checks that are known to fail instead of skipping them |

### Exploration

With the default seed and budget every run checks the same inputs, so in CI the laws
are deterministic regression tests. Searching for new counterexamples is the job of the
weekly GeomLaws workflow (`.github/workflows/GeomLaws.yml`), which runs `explore.jl` on
each law file with a fresh seed and 2000 examples per check. It can also be started by
hand from the Actions tab with a chosen seed and budget.

Exploration turns off Supposition's shrinker, which has no time limit, so a failure
prints the seed and the counterexample as found. To reproduce it:

```sh
GEOMLAWS_SEED=<seed> GEOMLAWS_EXAMPLES=2000 julia --project=. test/laws/explore.jl test_offset
```

To get a minimal counterexample, run the failing item through `TestItemRunner.run_tests`
as above with the same environment variables. Add it to the [ledger](#known-failures-the-ledger)
before changing the law or the code.

## What a passing run tells you

Each generative check runs its law on `GEOMLAWS_EXAMPLES` valid inputs. Inputs that
don't meet the law's preconditions are rejected and redrawn, and a check that rejects so
many that it gives up before reaching the budget (Supposition stops at 10 attempts per
requested example) *fails*: a law can't pass by testing fewer inputs. The test output
shows `N valid / M attempts` for every check.

What a pass establishes depends on the kind of law.

**Algebraic laws** compare the kernel's output with its own output on an equivalent
problem (swapped operands, regrouped operations, an operand transformed or in other
units, an offset done in two steps), or with the input where an identity gives the
answer (`A ∪ A = A`), or with each other (areas that must add up). They catch defects
that depend on operand order, decomposition, coordinate type, position, or
orientation. A defect that affects both sides alike passes them: an `xor2d` that
returned the union would still be commutative. B1–B6, B9, B10, O1, O2, O4–O6, T1, T2,
and D1 are algebraic laws.

**Oracle laws** compare the kernel's output with the true answer, computed exactly from
the operands without the kernel: point membership for the boolean operations (B7, B12),
and distance from the operand for round offsets (O3, O8) and path halos (O7). They
catch wrong answers that are self-consistent. O7 is the exception: the footprint it
measures distance from is the kernel's `union2d` of the path's pieces, and its upper
bound on the halo is the kernel's miter `offset` of the footprint. Other laws cover
both operations.

**Validity laws** check the structure of the output: contours that don't cross
themselves, outer/hole winding, holes inside their parents (B8), and well-formed keyhole
polygons (B11).

Two more things set the strength of a verdict:

  - **Tolerance.** Clipper rounds every vertex it computes to an integer grid, so most
    laws hold only to within a few grid units, stated per check (see
    [How outputs are compared](#how-outputs-are-compared)). For floating-point
    coordinates a grid unit is 1 fm, so these tolerances are far below anything a design
    cares about. For integer coordinates a grid unit is one coordinate unit, and the
    integer generators use small coordinates (about ±20) on purpose: there, rounding is
    as coarse relative to the geometry as it gets, which is where rounding bugs show.
  - **Exhaustive or sampled.** Region comparisons are exhaustive: they cover the whole
    plane, so a disagreement anywhere beyond the tolerance fails the check. Four laws are
    sampled instead: B7, B12, O3, and O7 check membership at a few hundred probe points
    per input: 256 uniform over the bounding box, plus 16 around each vertex and 16
    around each edge midpoint of every region, just outside the tolerance band. They can
    miss a disagreement that falls between probes. O8 complements O3 with an exhaustive
    bound, on convex inputs.

At the default budget each check sees the same 50 inputs every time. Roughly, a defect
that one generated input in 100 triggers has a 40 % chance of being among them, and a
weekly run with 2000 inputs per check is all but certain to find it.

This is evidence that the suite is sensitive to these defect classes, not a proof that
it catches every defect in them. Every mutant treats both operand orders alike and
commutes with rigid transforms, so B1 and T1 catch none of them; those laws target
other defects.

## How outputs are compared

**The grid.** `clipperize` passes integer coordinates (including integer `Quantity`s) to
Clipper unchanged and scales floating-point coordinates to integers in femtometers.
`togrid` maps vertices onto the same grid, so the exact predicates see exactly what the
kernel saw, and tolerances are stated in grid units. The vertices are on the grid, but
the regions between them are continuous: comparisons are between regions of the plane,
not between sets of grid points.

**Reading contours.** A list of contours is read with the even-odd rule. That is the
right reading of a `ClippedPolygon` tree (outer contours counterclockwise, holes
clockwise) and of keyhole polygons with zero-width cuts. It is not the right reading of
arbitrary overlapping input polygons, which DeviceLayout fills with the positive rule,
so the comparisons are applied to outputs and to operands that don't overlap.

**Comparisons** (in `lawslib.jl` and `region_oracle.jl`):

| Function                        | Passes when                                                                                                                                                |
|:------------------------------- |:---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X ≐ Y`                         | The canonical contours are identical: after removing repeated and collinear vertices, fixing orientation and starting vertex, and sorting                  |
| `region_same(X, Y)`             | `X` and `Y` are the same region, however they are divided into contours (for example two contours touching at a vertex, or one contour with a pinch there) |
| `region_within(X, Y, t)`        | Every point in exactly one of `X` and `Y` is within distance `t` (inclusive) of the boundary of `X` or `Y`                                                 |
| `region_subset_within(X, Y, t)` | The same, checked only for points in `X` but not in `Y`                                                                                                    |

`region_same` and `region_within` sweep vertical lines through every vertex and every
edge crossing of both boundaries, in `Rational{BigInt}`. Between neighboring lines the
edges cut the strip into trapezoids, each entirely inside or outside each region, so any
trapezoid inside exactly one region is a disagreement and `region_same` fails. For
`region_within`, each disagreement must be shown to lie within `t` of the boundary: it is
split into triangles, and a triangle is covered if all three corners are within `t` of
one boundary edge (that neighborhood of a segment is convex). Triangles that aren't
covered are subdivided until the check either covers them, finds a point farther than
`t` from every edge (a failure), or exhausts its work budget, which also fails, as
`:inconclusive`. Before any of this, edges where membership doesn't change are
cancelled: the seam between two touching contours, or a keyhole cut traversed in both
directions, would otherwise excuse a disagreement next to it.

So: a disagreement fails the comparison unless all of it is within `t` of a boundary,
however thin it is; zero-area decorations such as a pinch or a zero-width spike don't
count; and agreeing areas or agreeing samples never establish equality, outside the
four sampled laws.

**Offsets.** `offset_class` decides exactly whether a point is inside the true offset of
a polygon, outside it, or within the tolerance band of its boundary, from the polygon
alone. O3 uses it at probe points. O8 instead checks every output edge along its whole
length: for a positive round offset of a convex polygon, each edge must lie between
δ − t and δ + t from the polygon, the lower bound by an exact segment-to-segment
distance and the upper bound by the same covering argument as `region_within`. The
check requires a convex polygon and refuses anything else, because only then is the
distance to the offset boundary |dist(q, A) − δ|; where the offset fronts of a nonconvex
polygon merge, that identity fails. On integers t is 2 grid units. On floats, O8 uses the
default arc tolerance `atol` of 1 nm and allows 2.25 nm on top of the 2 units, because
Clipper1 rounds the number of chords per corner, so a chord can deviate from the arc by
up to 2.25 `atol`. O8 doesn't check that no component is missing; O3 and the
algebraic laws do.

**Output size.** Region comparisons give up, failing the check, when the two regions
have more than 4000 vertices between them. The sweep is quadratic in edge count, and an
output that size from inputs of a few dozen vertices is itself a finding.

## Inputs

Generators (in `lawslib.jl`) build valid inputs by construction, validate them exactly,
and reject anything invalid. They never call the clipping kernel. Every generated
polygon is simple and counterclockwise; holes in generated trees are clockwise, as
Clipper returns them.

| Generator                                      | Draws                                                                                                                                                                                                                                                                         |
|:---------------------------------------------- |:----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `int_star_polygon`                             | Star-shaped polygons with 3–12 vertices rounded onto the integer grid [−20, 20]², which creates collinear triples and near-touching vertices                                                                                                                                  |
| `int_thick_star_polygon`                       | The same, without vertices within 1.5 units of a non-adjacent edge (thinner ones can vanish, ledger L1)                                                                                                                                                                       |
| `int_rectilinear_polygon`                      | Staircases with up to 5 steps. Every edge crossing of two rectilinear polygons is a grid point, so laws on them hold exactly                                                                                                                                                  |
| `int_rectangle_polygon`, `int_convex_polygon`  | Rectangles, and near-regular convex polygons for O8                                                                                                                                                                                                                           |
| `float_star_polygon`                           | Star polygons with feature sizes from about 1 nm to 100 μm                                                                                                                                                                                                                    |
| `int_pair`, `degenerate_pair`                  | Two thick integer stars, the second shifted by up to 10 units each way; or a rectangle with a partner that is a translated copy (identical, overlapping, or disjoint), shares an edge, touches a corner, has an extra collinear vertex, or is a one-unit strip along its edge |
| `float_star_pair`                              | Two float stars of the same size, the second shifted by up to half that size                                                                                                                                                                                                  |
| `float_perturbed_pair`                         | A float star and a copy with one vertex moved by k = 1–10 fm, or a sliver k fm wide along one edge. Their edges nearly coincide, which makes every intersection ill-conditioned, so laws on these pairs hold within k + 2                                                     |

| triples, `*_polygon_set`                       | Three operands; sets of 2–6 polygons spread over an area a few times their size                                                                                                                                                                                               |
| `int_necked_polygon`, `int_cavity_polygon`     | Rectilinear dumbbells and cavities, whose offsets change topology: erosion splits a dumbbell at its neck, growth closes a cavity's mouth into a hole                                                                                                                          |
| `int_holed_polygon`, `int_multi_holed_polygon` | `ClippedPolygon` trees built directly (not by clipping): one hole; or 2–6 holes in a grid of cells, some with islands, so that one hole's keyhole cut runs into another hole                                                                                                  |

`Data.Floats`: that draws bit patterns, which puts about a quarter of draws within 1e-3
of the lower bound. Vertex counts are drawn separately, because the shorter of two
independently sized vectors is usually length 3 at small budgets.

### Offsets and halos (`test_offset.jl`)

Several offset laws are stated only where |δ|·sin(turn) ≥ 1 grid unit at every vertex
(`well_conditioned_offset`): below that, Clipper1 can misplace a sharp corner by up to δ
(ledger L7, L10). Laws that offset an offset result allow `offset_tol`, 2 + ⌈|δ| / 2L⌉
for L the shortest edge of the first result: an edge of length L whose ends are each
rounded by half a unit points up to about 1/(2L) off, and offsetting it by δ moves its
ends by about δ/(2L) (ledger L9).

### Tests of the test machinery

`test_fixtures.jl` and `test_oracle_regressions.jl` check the predicates, the generators'
guaranteed degeneracies, and the comparisons themselves on inputs where the answer is
known: disjoint strips that no grid point lies inside, a disagreement whose only
witnesses are off the grid, equivalent decompositions, a coarse bevel that O8 must
reject, an exhausted work budget, and a check that rejects every input. If a comparison
is loosened, these fail.

## Known failures: the ledger

`test_ledger.jl` holds a minimal fixed input for every law violation found so far, with
an explanation of the mechanism. Assertions that fail on the current code are written
`@test_broken`, so a change that fixes one shows up as an unexpected pass. The
generative checks they affect are skipped through `KNOWN_BROKEN` in `lawslib.jl`.

| Entry | Finding                                                                                 | Source         | Status                                           |
|:----- |:--------------------------------------------------------------------------------------- |:-------------- |:------------------------------------------------ |
| L1    | An integer polygon with a vertex within a unit of an edge vanishes under `union2d([A])` | Clipper1       | Broken; B3 and O1 skip thin integer polygons     |
| L2    | Union output can touch itself at a vertex                                               | Clipper1       | Tolerated: B8 allows touching                    |
| L3    | Integer union output can cross itself after rounding                                    | Clipper1       | Broken; B8 skips integer stars                   |
| L4    | A hole vertex can land outside its parent after rounding                                | Clipper1       | Broken; B8 skips nesting on stars                |
| L5    | `to_polygons` throws on a hole whose lowest vertex is outside its parent                | `interiorcuts` | Pinned (#350); B11 rejects such trees            |
| L6    | Zero-length edges at keyhole cuts                                                       | `interiorcuts` | Fixed (#350); regression test                    |
| L7    | A small offset leaves a sharp input vertex in place                                     | Clipper1       | Broken; offset laws need well-conditioned inputs |
| L8    | A 2 fm sliver makes `difference2d` output cross itself                                  | Clipper1       | Broken; B8 skips perturbed pairs                 |
| L9    | A 1 fm edge in one offset's output misdirects the next offset                           | Clipper1       | Broken; tolerances use `offset_tol`              |
| L10   | Square and miter offsets cut a sharp tip after a near-collinear vertex                  | Clipper1       | Broken; O4 needs well-conditioned inputs         |
| L11   | A keyhole cut rounded to the grid can make the polygon cross itself                     | `interiorcuts` | Warns; B11 accepts it with the warning           |
| L12   | Taper halos are short of δ along slanted sides and overhang at the narrow end           | `halo`         | Broken (#8)                                      |
| L13   | Halos with an inner offset are open at the path ends                                    | `halo`         | Broken (#8)                                      |
| L14   | A cut next to another hole's cut can cross that hole without a warning                  | `interiorcuts` | Broken                                           |
| L15   | After a warned cut, a later hole can fail to attach, and `to_polygons` throws           | `interiorcuts` | Accepted; B11 treats the error as the warning    |

## What isn't covered

**Operations.** Curves are not tested: `CurvilinearPolygon` discretization, the
`*_curved` booleans, and curve recovery. Nor are `*_layerwise` operations, `render!`,
GDS input and output, or solid models. Fill rules other than the default are tested
only with union (`clip(ClipTypeUnion, ...)`). `offset` is tested only on closed
polygons, not open paths, and there is no law about the miter limit, which `offset`
doesn't document. Halos are tested only for `Trace`, `CPW`, and taper paths of
straight and turning segments. Transforms are rigid only: no magnification. Unitful
coordinates appear only in T2 and D1. No law asserts when `to_polygons` should warn.

**Input sizes.** Generated polygons have at most 15 vertices, apart from discretized
paths; sets have at most 6 polygons, and trees at most 6 holes. Integer coordinates stay
within a few hundred units, and float inputs within 1 cm of the origin. Large
real-design polygons are exercised only by the differential harness's corpus, outside
the test suite.

**Input shapes.** Generated operands are simple, counterclockwise `Polygon`s.
Self-overlapping or clockwise operands appear only as reversed contours in B9 and as
kernel output reused in B12, and polygons with holes only through their contours (B11,
B12).

**Excluded regimes.** A law stated away from a known-bad regime says nothing about that
regime beyond its ledger entry: offsets with |δ|·sin(turn) below a grid unit (L7, L10),
thin integer polygons (L1), self-crossing union output in the B3 fixed-point check
(L3), trees with holes outside their parents in B11 (L4, L5), invalid first results in
B12, corners under 60° in the miter semigroup law, and nonconvex or eroding inputs in
O8. Float round joins are tested with `atol = |δ|/200` except in O8, which uses the
1 nm default.

**Runtime.** Kernel run time isn't tested. The comparisons' work budget bounds only the
comparison, not a call into Clipper, so a kernel call that hangs hangs the test.

## Changing or adding laws

  - Add a check to the file for its group as `@lawcheck function name(x=generator, ...)`,
    returning `true` or `false`. Call `reject!()` for inputs that don't meet the law's
    preconditions; the budget check keeps rejection from starving the law.
  - State the tolerance in grid units and say in a comment where it comes from, usually
    the number of rounding steps on each side.
  - Prefer a region comparison to sampling. Never turn an inconclusive certificate into a
    pass; if a comparison is too slow, find out why.
  - New generators build valid inputs by construction, validate them exactly, and don't
    call the clipping kernel.
  - Add a mutant the new law should catch to `mutants/mutants.jl`, and check that it does.
  - If the law fails on the current code, add a minimal input to the ledger with
    `@test_broken`, add an id to `KNOWN_BROKEN` with a comment naming the entry, and wrap
    the check in `@law :id`. When a fix makes a ledger assertion pass, change it to
    `@test` and remove the id.
  - Measure the runtime on the CI matrix before raising the default budget.
