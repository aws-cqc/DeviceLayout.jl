Conventions

Rules for writing code in DeviceLayout.jl. They apply to new and changed code. Existing code doesn't follow all of them, and isn't changed just to conform. On this page we highlight conventions that are not obvious from context (especially in older ports of the code), are specific to DeviceLayout.jl, or simply come up frequently. Conventions for tests and docs are in Writing tests and Documentation.

Substantive conventions

Some rules are particularly consequential:

Units and coordinate types. Almost all geometry is parameterized by a coordinate type T <: Coordinate = Union{Real, Length}. Code must work for unitless Float64 (interpreted as microns), for Unitful lengths, and (in some places) for Int. Functions that take more than one unitful coordinate should work when they have different types. Use zero(T), oneunit(T), DeviceLayout.onenanometer(T), DeviceLayout.onemicron(T), and ustrip(unit, x) rather than assuming a unit.

Tolerances. Curve discretization defaults to atol = onenanometer(T); Clipper works on coordinates rounded to an Int64 femtometer grid by clipperize. When comparing geometry, prefer isapprox with an explicit atol over ==.

Generated names. uniquename appends a counter from a process-global, thread-safe dictionary; it is deterministic only in a fresh session or after calling reset_uniquename!(). If you need to generate a unique name (schematic node id, coordinate system name), use uniquename to avoid collisions, and allow the user to explicitly provide a name. Auto-generated names are not part of the public API (see What counts as breaking?).

Fallbacks. A fallback that dispatches on an abstract type must be correct for every subtype that could ever reach it, including ones that don't exist yet. If you can't guarantee that, throw instead. A fallback used as a common default gives a new subtype silently wrong answers rather than a MethodError.

Logging. Use @warn/@info from Logging, never println, for anything a user should see. Many tests assert on logs (see Writing tests), so a stray warning can be a test failure. Warn when a designer should know a result may not be what they expect, and sparingly otherwise. Throw an error rather than guess at what the user intended (see Design Principles).

Global state. Avoid adding global state, but be aware that it is used in a few places:

  • __init__ creates the global Clipper handle (_clip) and registers FileIO formats. precompile.jl duplicates both because __init__ has not run during precompilation. Clipping through _clip is not thread-safe.
  • SolidModels wraps a single global Gmsh session, and the mesh-size callback installed by render! or set_mesh_size_callback! is global to it. Tests that touch it use the QuietGmshSetup snippet to initialize it and silence output.
  • MESHSIZE_PARAMS (solidmodels/solidmodels.jl) holds global scalar mesh settings (scale, order, default grading, respect_lc) as well as the mesh-size control points and their KD-trees. render! clears the control points, but the scalar settings persist across models until changed.
  • The uniquename counter, the Memoization cache for B-spline tangent optimization, and the PolyText font caches are process-global.
  • Some warnings are shown once per session: deprecation warnings with maxlog=1 (see Deprecations), and recover_curves warns once per entity type about lost curves. Test items share a process, so a test asserting such a warning depends on nothing earlier having triggered it.

Style

DeviceLayout.jl generally follows the Julia manual's style guide and Blue style, but consistency with existing code takes priority. Layout is whatever JuliaFormatter produces with .JuliaFormatter.toml, which CI enforces (see Formatting), so formatting is never a review topic. Remaining style decisions can be settled by SciMLStyle when it has an applicable rule.

Mutation. Functions and methods that mutate any of their arguments have names ending in !. Mutated arguments come before non-mutated arguments, following SciMLStyle's function argument precedence.

Leading underscores. A name beginning with _ is not called by users. It is either a private helper or an interface method that users implement but don't call, like _geometry!, _graph!, _build_subcomponents, and _route_leg!. New private helpers within a source file should begin with _. New methods used across source files should not use a leading underscore, even if they are not public (exported, documented, or part of an interface that users implement).

Variables. Names reflect the actual type of the value they hold, not a related concept. For example, a ComponentNode is node, never comp (the component it wraps is node.component); a SchematicGraph is g, not sch for Schematic (though also avoid graph, which is a function exported by .SchematicDrivenLayout); a Cell is c, not cs (which denotes a CoordinateSystem). In a small scope where the type is obvious from context or a type annotation (a comprehension, a short loop body, a short function with annotated arguments), use very brief names. In a large scope, or where nothing lets a reader infer the type, use longer descriptive names.

Extending functions from other modules. Define methods with a qualified name (SchematicDrivenLayout.hooks(c::MyComp) = ...). If the function is imported, then Julia will accept the bare name as referring to the imported function, but prefer the qualified name for clarity and protection against a deleted import.

Comments. Comments explain why the code is the way it is, so future readers know what's safe or necessary to change. Comments are evergreen and do not make historical references ("refactored", "new", "improved", "fixed").

Example code follows the component style guide.
