Contributing

How to set up a development checkout, run and write tests, format code, build the docs, decide whether a change is breaking, and get a change reviewed and merged. Contribution etiquette (issues first for large changes, fork-and-PR, licensing) is in CONTRIBUTING.md.

Setup

git clone https://github.com/aws-cqc/DeviceLayout.jl
cd DeviceLayout.jl
julia --project=. -e 'using Pkg; Pkg.instantiate()'

--project=. activates the package's own environment. You can also ] dev /path/to/DeviceLayout.jl from another environment (for example a PDK or design project) to test your change against real downstream code.

Optional pieces:

  • TestEnv in your default environment (] add TestEnv outside the project) to run individual test items without going through Pkg.test().
  • Revise in your default environment (] add Revise), which can be imported before a package under development to automatically reload changed code without restarting Julia.
  • VS Code Julia extension if you want the Testing sidebar (see below).
  • Python + ezdxf for the deprecated DXF export and its test: pip install -r requirements.txt. The test calls python3 from PATH; without ezdxf, the "DXF export" testset in the "Deprecations" test item fails. Everything else works without Python.

Reviewers who just want to try a branch can ] add DeviceLayout#branch-name for a branch on the main repository, or ] add https://github.com/<user>/DeviceLayout.jl#branch-name for a branch on a fork.

Testing

The suite uses TestItemRunner: each @testitem in test/*.jl is an independent unit that runs in its own module. test/runtests.jl defines shared @testsnippets and calls @run_package_tests with a filter that matches test-item names against ARGS.

Running tests

  1. Full suite, CI-equivalent. With the package as active project:
    using Pkg; Pkg.test()
    To run only test items whose names contain any of some strings:
    Pkg.test(test_args=["Routes", "Polygon clipping"])
  2. CLI. From the package root directory, the full suite (via Pkg.test()) or, with arguments, the items whose names contain any of them (via TestEnv, as in 4):
    julia --project=. scripts/test.jl
julia --project=. scripts/test.jl "Routes" "Polygon clipping"
  3. VS Code. Open the repo folder and use the Testing sidebar (beaker icon). Individual test items can be run, debugged, or run with coverage.
  4. Targeted, in a REPL. With TestEnv available and the package as active project:
    using TestEnv; TestEnv.activate()
using TestItemRunner
import DeviceLayout
TestItemRunner.run_tests(pkgdir(DeviceLayout); filter=ti -> ti.name == "Backends")
    The filter receives (; filename::String, name::String, tags::Vector{Symbol}); filename is an absolute path.
Don't invoke `@run_package_tests`

Never invoke @run_package_tests from the REPL or -e; it expands to run_tests(joinpath(dirname(__source__.file), "..")), which outside a file is the parent of the current directory (every sibling checkout). Call run_tests with an explicit path instead.

Use the test environment

Use TestEnv.activate() rather than running tests in the checkout's project directly: some tests write preferences, and TestEnv keeps them out of the repo's Project.toml/LocalPreferences.toml. Tests also have some additional dependencies that are not present in the package's own project environment.

On Julia versions before 1.13, Pkg.test() runs with --check-bounds=yes, so it can't reuse the precompile cache from development and recompiles DeviceLayout and its dependencies. Prefer the TestEnv routes for iteration on those versions.

Pkg.test() also runs with --depwarn=yes, which the TestEnv routes do not. Without it, Base.depwarn is silent and @test_deprecated checks nothing, so the "Deprecations" test item only fully tests those deprecations under Pkg.test().

CI runs the full suite on every released Julia minor from 1.10 upward. Pre-release Julia is allowed to fail but failures should be investigated.

Writing tests

  • Put new tests in the topical test_<topic>.jl file, or create one. Use @testitem with the shared setup snippet: setup = [CommonTestSetup] (plus QuietGmshSetup for anything that touches Gmsh).

  • Name test items descriptively and reference the issue when the test is a regression test: @testitem "Zero-length turns are ignored (#269)". Names are what the CLI filter matches on.

  • Assert on logs. Warnings are part of the contract. Use with_test_logger, with_expected_info, or quiet_test_output from the snippet to require that expected warnings appear and no others do, or @test_logs directly. Unexpected warnings in a test are failures, not noise. The log should be quiet when tests are passing.

  • Unitful and unitless. If the code under test is generic in the coordinate type, test Length types as well as Float64. The snippet's μm2nm, μm2μm, etc. let you test mixed-preference arithmetic without changing the compile-time preference.

    Test environment units

    Only the default unit preference (PreferNanometers) is tested in CI. The test suite's μm, nm, etc. are imported from Unitful (no preference), not PreferNanometers. Tests that pass in a user environment can fail in the test environment, or vice versa, depending on unit preference and how unit symbols were imported in the user environment.

  • Geometry comparisons should use isapprox with an explicit atol, or compare invariants (area, perimeter, vertex count, is_sliver) rather than raw vertex lists, unless the vertex list is the contract.

  • Files written during tests go under tdir (a mktempdir() from the snippet).

Formatting

CI rejects unformatted code. Format with

julia scripts/format.jl format

which installs JuliaFormatter v1 into a temporary environment (so it resolves the way it would in CI) and formats src/, test/, and scripts/ according to .JuliaFormatter.toml. julia scripts/format.jl check reports without modifying. Docstrings are also formatted (format_docstrings = true), so a formatting-only diff inside a docstring is normal.

Documentation

Docs are built with Documenter from docs/src/, with the page tree in docs/make.jl. Docstrings are pulled in via @docs blocks on the Reference and Examples pages; a docstring that isn't listed anywhere is silently omitted because checkdocs=:none.

Previews. Every pull request gets a preview at https://aws-cqc.github.io/DeviceLayout.jl/previews/PR<number>/, deleted when the PR closes. This is usually the fastest way to review docs changes.

Local build.

julia --project=docs -e 'using Pkg; Pkg.develop(PackageSpec(path=pwd())); Pkg.instantiate()'
julia --project=docs docs/make.jl

Expect several minutes: the @example blocks run real code, including the QPU17 example. If the build dies with MissingRemoteError for a CoordinateTransformations docstring, run Pkg.develop("CoordinateTransformations") in the docs environment: the Reference pages include its docstrings, and Documenter needs a git checkout to generate source links. (This adds a local path to docs/Project.toml under [sources]; don't commit that.) Because prettyurls=true, the output in docs/build/ needs a web server rather than file://; for example using LiveServer; serve(dir="docs/build").

Check for warnings. warnonly=true means broken @ref links, missing docstrings, and failed doctests produce warnings, not errors. Scan the log for Warning before merging docs changes.

Conventions. New user-facing concepts go under docs/src/concepts/, task-oriented material under tutorials/ or how_to/, and API listings under reference/. For more on the distinctions between these kinds of documentation and how to write each effectively, see Diátaxis. This "Developer Guide" section is for material that only matters if you're changing the package itself.

Benchmarks

benchmark/ is a PkgBenchmark suite (benchmarks.jl defines SUITE; topical files add groups for autofill, bounds, clipping, curves, intersections, polygons, and schematics). It has its own environment:

julia --project=benchmark -e 'using Pkg; Pkg.develop(PackageSpec(path=pwd())); Pkg.instantiate()'
julia --project=benchmark -e 'include("benchmark/run_benchmarks.jl")'

run_benchmarks.jl writes benchmark.md and prints a summary. The Benchmark GitHub workflow runs the same thing on demand (workflow_dispatch) and uploads benchmark.md as an artifact. To compare two commits, use PkgBenchmark.judge directly.

Benchmarks are not run on every PR. If a change is performance-motivated, include before/after numbers in the PR description.

When adding benchmarks, you may need to delete benchmark/tune.json so it can be regenerated.

Pull requests and review

What a pull request includes

Authors check this list before asking for review, and reviewers check the same list.

  • Scope. Every changed line traces to the stated purpose. Don't reformat or refactor code you aren't otherwise touching.

  • Conventions. New and changed code follows Conventions.

  • Tests. New tests for new behavior, and a regression test for any bug fix (see Writing tests).

  • Changelog. An entry in CHANGELOG.md as described in Changelog. Decide whether the change is breaking using What counts as breaking?; if it is, make it opt-in on main or target v2.0.0-dev (see Opt-in first).

  • Documentation. Docstrings are updated for any changed public API, new public API functions are added to the appropriate API reference page, concept pages, and the developer guide are updated if the change moves files or alters behavior they describe. The docs build does not fail on warnings, and some breakage only produces warnings, so check the log when relevant. See Documentation above.

  • Third-party code. Code adapted from another project has a compatible license and an entry in THIRDPARTY.md, and the PR description says so.

  • Title and description. PRs are squash-merged, so the title becomes the commit summary: make it a succinct one-line description of the change. The description links the issue it addresses, gives a brief but complete account of the changes, and states the breaking-change assessment. Changes to rendered geometry are highlighted even if they are not breaking.

    Commit messages within the PR take the same form: a succinct one-line summary, then a brief but complete description of the changes in the body.

CI and merging

Required checks on main are: formatting, documentation build, and tests on each released Julia minor version in the CI matrix. Tests only start once the formatting check passes, so run julia scripts/format.jl format and the tests locally before pushing. A PR can merge once the checks pass and a maintainer has approved.

Reviewing

Reviewers check the items above in What a pull request includes. They also review contributions not just on their own terms but in terms of the package's overall direction, design, and code health. Some typical questions a maintainer will ask are listed below, but contributors using agents are encouraged to use their own review instructions to avoid tunnel vision on criteria mentioned here and increase the diversity of approaches used for review.

Premise:

  • Is the right problem being solved?
  • Is this the right solution?
  • Can the solution be simplified?

Design implications:

  • Do the changes fit the existing design?
  • Do the changes reveal deficiencies in the existing design (e.g. simple behavior change requires complex code changes)?
  • Do the changes lock in one-way decisions?
  • Do the changes follow the design principles?

Clarity:

  • Can the code be understood at a glance?
  • Do the comments add value to the surrounding code?
  • Is the code in the right place?

Correctness:

  • Is the code clear enough to evaluate correctness by hand, or are there places for bugs to hide?
  • Have edge cases been foreseen?
  • Do the unit tests adequately test the code? The coverage report does not account for different types that can be used in the same code path.

Reused and duplicated code:

  • Is code duplicated within the package?
  • Is there local functionality that should be in a shared library?
  • Is there code that could be completely removed or replaced with existing libraries?

Failure handling:

  • Is the code resilient to garbage and null inputs?
  • If a user encounters an error, will they understand what went wrong and where?
  • Is there a clear and consistent exception handling strategy?

Performance:

  • Are there signs of premature optimization?
  • Are there obvious performance or efficiency problems?
